# AetnaMem 0.6.1.1a4 — two clear memory states

Status: **experimental preview**

This prerelease simplifies OpenClaw adoption around the only decision a user
needs to make:

> Keep OpenClaw memory active while AetnaMem mirrors it, or activate AetnaMem
> and retain a verified path back to OpenClaw.

Matching packages:

- Python: `aetnamem==0.6.1.1a4`
- OpenClaw bridge: `openclaw-memory-aetnamem@0.4.1-experimental.3`

The npm bridge is unchanged in this release. The Python engine still installs
and verifies it automatically.

## Install or update

```bash
python -m pip install --upgrade --pre aetnamem==0.6.1.1a4
aetnamem --version
aetnamem openclaw install
```

Existing mirrored memory, frozen native snapshots, and trial evidence are not
deleted by the package update.

## What changed

- The dashboard now has one page and two customer-visible states:
  **OpenClaw active** and **AetnaMem active**.
- Memory search accepts ordinary words and shows source path and line
  provenance.
- The dashboard lists exactly which source files are mirrored, including byte
  count, memory plane, and complete SHA-256 digest.
- One guarded control activates AetnaMem; the same location restores OpenClaw
  after activation.
- Preview, canary, candidate-review, emergency-off, chart, funnel, and mock
  comparison controls were removed from the customer interface.
- Direct mirror-to-active transition is supported after mirror and audit
  readiness checks pass.
- The CLI adoption surface is reduced to `start`, `status`, `activate`,
  `rollback`, `dashboard`, and the private integration server.
- Human-readable status reports the active memory provider, mirrored source
  count, searchable memory count, mirror verification, and audit-chain health.
- Documentation now uses the same two-state language throughout.

## Safety retained

Simplifying the interface does not remove the safety work. Activation still
takes and verifies the final mirror and native snapshot, checks unsupported
OpenClaw memory capabilities, verifies the gateway, tools and hooks after
restart, and restores the prior state automatically if cutover fails.

Rollback remains the supported route back because it restores and verifies
usable OpenClaw memory instead of leaving both memory systems inactive.

Legacy internal state values remain readable for evidence and upgrade
compatibility, but they are no longer exposed as customer workflow choices.
